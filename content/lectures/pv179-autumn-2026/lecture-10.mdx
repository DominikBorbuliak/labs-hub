# Caching with `IMemoryCache`

## Why?

Some data is read often but changes rarely: a post detail, a list of categories, the home page. Instead of asking the database every time, keep the result **in memory** for a while.

| Type               | Where the data lives            | Use when                                 |
| ------------------ | ------------------------------- | ---------------------------------------- |
| **In-memory**      | RAM of the app (`IMemoryCache`) | One instance of the app (your project)   |
| **Distributed**    | Redis, SQL Server, ...          | Several instances must share one cache   |
| **Output caching** | Whole HTTP responses            | The entire page is the same for everyone |

## Usage

`IMemoryCache` is registered by `builder.Services.AddMemoryCache()` (MVC already does it for you) and injected like any other service. `GetOrCreateAsync` returns the cached value, or runs the factory, stores the result and returns it:

```csharp
public class PostService(IUnitOfWork unitOfWork, IMemoryCache cache) : IPostService
{
    public async Task<PostDto?> GetByIdAsync(int id)
    {
        return await cache.GetOrCreateAsync($"post:{id}", async entry =>
        {
            entry.AbsoluteExpirationRelativeToNow = TimeSpan.FromMinutes(5);

            var post = await unitOfWork.Posts.GetByIdAsync(id);
            return post?.Adapt<PostDto>();
        });
    }
}
```

The same thing written by hand is `TryGetValue` (hit → return it) and `Set` (miss → load and store).

## Expiration

| Option       | Behavior                                                             |
| ------------ | -------------------------------------------------------------------- |
| **Absolute** | Removed after a fixed time, no matter how often it's read            |
| **Sliding**  | Removed after a time **without access**, every read resets the timer |
| **Both**     | Sliding, but never longer than the absolute limit                    |

> [!WARNING]
> With **only** sliding expiration, an entry that is read often **never expires**, so it can stay outdated forever. Combine it with an absolute limit.

## Invalidation

When the data changes, remove the old entry, otherwise users see the old version until it expires:

```csharp
public async Task UpdateAsync(PostUpdateDto dto)
{
    // ... update and save ...
    cache.Remove($"post:{dto.Id}");
}
```

- **Cache DTOs**, not entities. An entity belongs to the request's `DbContext`: in later requests its unloaded navigation properties are `null`, and every request shares (and can change) the same object
- **The key must contain everything the result depends on**: `post:{id}`, or `feed:{userId}:{page}` for per-user data

## `HybridCache`

The newer cache (.NET 9+), recommended for new projects. Package `Microsoft.Extensions.Caching.Hybrid`, registered with `builder.Services.AddHybridCache()`:

```csharp
public class PostService(IUnitOfWork unitOfWork, HybridCache cache) : IPostService
{
    public async Task<PostDto?> GetByIdAsync(int id, CancellationToken ct = default)
    {
        return await cache.GetOrCreateAsync(
            $"post:{id}",
            async token => (await unitOfWork.Posts.GetByIdAsync(id, token))?.Adapt<PostDto>(),
            new HybridCacheEntryOptions { Expiration = TimeSpan.FromMinutes(5) },
            tags: ["posts"],
            cancellationToken: ct);
    }

    public async Task UpdateAsync(PostUpdateDto dto)
    {
        // ... update and save ...
        await cache.RemoveByTagAsync("posts"); // removes every entry tagged "posts"
    }
}
```

|                                      | `IMemoryCache`                               | `HybridCache`                                            |
| ------------------------------------ | -------------------------------------------- | -------------------------------------------------------- |
| 10 requests for the same missing key | Factory runs 10× (10 DB queries)             | Factory runs **once**, the others wait                   |
| Invalidation                         | Only by key                                  | By key **or by tag**                                     |
| Several app instances                | Each has its own cache, they get out of sync | Add Redis and it's used as a shared 2nd level, same code |

> [!TIP]
> [MS Learn: Cache in-memory in ASP.NET Core](https://learn.microsoft.com/en-us/aspnet/core/performance/caching/memory) · [MS Learn: HybridCache](https://learn.microsoft.com/en-us/aspnet/core/performance/caching/hybrid)

# EF Core Queries

The queries in this and the next sections belong in the **DAL** (repositories and query objects), where `context` is the `AppDbContext`.

## `IQueryable` vs `IEnumerable`

|         | `IQueryable<T>`                    | `IEnumerable<T>`            |
| ------- | ---------------------------------- | --------------------------- |
| Runs    | In the database, translated to SQL | In memory, in C#            |
| Example | `context.Posts.Where(...)`         | `posts.ToList().Where(...)` |

Everything after `ToList()` or `AsEnumerable()` runs in memory, **on all loaded rows**:

```csharp
// ❌ loads ALL posts, then filters and pages in C#
var posts = context.Posts.ToList().Where(p => p.CreatorId == id).Take(10);

// ✅ WHERE and TOP/LIMIT in SQL, loads 10 rows
var posts = await context.Posts.Where(p => p.CreatorId == id).Take(10).ToListAsync();
```

## Deferred Execution

An `IQueryable` is only a **description** of the query. It runs when you ask for the results: `ToListAsync`, `FirstOrDefaultAsync`, `CountAsync`, `AnyAsync`, `foreach`. Until then you can keep adding to it, which is how optional filters (search) are built:

```csharp
IQueryable<Post> query = context.Posts;

if (!string.IsNullOrWhiteSpace(search))
{
    query = query.Where(p => p.Title.Contains(search));
}

if (creatorId is not null)
{
    query = query.Where(p => p.CreatorId == creatorId);
}

var posts = await query.ToListAsync(); // one SQL query with all the filters
```

## Seeing the SQL

```csharp
var sql = query.ToQueryString(); // the SQL, without running it
```

Or log every command EF Core sends, in `appsettings.Development.json`:

```json
"Logging": {
  "LogLevel": {
    "Microsoft.EntityFrameworkCore.Database.Command": "Information"
  }
}
```

> [!TIP]
> For read-only lists, use `AsNoTracking()` and `Select` only the columns you show. Less data loaded, no change tracking overhead.

# Pagination

## Offset Pagination

The classic "page 1, 2, 3 ..." with `Skip` and `Take`. You need **two queries**: one for the items, one for the total count (to know how many pages there are):

```csharp
public record PagedResult<T>(IReadOnlyList<T> Items, int TotalCount, int Page, int PageSize)
{
    public int TotalPages => (int)Math.Ceiling(TotalCount / (double)PageSize);

    // converts the items (e.g. entities → DTOs), keeps the paging info
    public PagedResult<TOut> Map<TOut>(Func<T, TOut> map)
        => new(Items.Select(map).ToList(), TotalCount, Page, PageSize);
}

public static class PagingExtensions
{
    public static async Task<PagedResult<T>> ToPagedResultAsync<T>(
        this IQueryable<T> query, int page, int pageSize, CancellationToken ct = default)
    {
        page = Math.Max(page, 1);
        pageSize = Math.Clamp(pageSize, 1, 100); // never trust ?pageSize=1000000

        var totalCount = await query.CountAsync(ct);
        var items = await query
            .Skip((page - 1) * pageSize)
            .Take(pageSize)
            .ToListAsync(ct);

        return new PagedResult<T>(items, totalCount, page, pageSize);
    }
}

var result = await context.Posts
    .OrderByDescending(p => p.CreatedAt)
    .ThenByDescending(p => p.Id)
    .ToPagedResultAsync(page, pageSize);
```

> [!IMPORTANT]
> Always `OrderBy` before `Skip` / `Take`, and make the order **unique**: two posts can have the same `CreatedAt`, so add `ThenBy` on `Id` as a tie-breaker. Without it, the database may return rows in a different order on every request, so the same post can show up on two pages.

## Keyset Pagination

Instead of "skip 1000 rows", remember the **last item you showed** and continue after it:

```csharp
// first page: lastId = null
var posts = await context.Posts
    .Where(p => lastId == null || p.Id < lastId)
    .OrderByDescending(p => p.Id)
    .Take(pageSize)
    .ToListAsync();

// next page: /posts?lastId=<Id of the last post on this page>
```

|                       | Offset (`Skip` / `Take`)                    | Keyset (`Where Id < last`)         |
| --------------------- | ------------------------------------------- | ---------------------------------- |
| Jump to page 57       | ✅                                          | ❌ only next / previous            |
| Speed on deep pages   | Slower, the DB still reads the skipped rows | Same on every page (uses an index) |
| New rows while paging | Items shift, duplicates or skipped items    | Stable                             |
| Typical use           | Admin tables, search results                | Infinite scroll, feeds, APIs       |

> [!TIP]
> [MS Learn: Pagination in EF Core](https://learn.microsoft.com/en-us/ef/core/querying/pagination)

# Query Objects

## The Problem

Lists need filtering, sorting and paging, in many combinations. Put into a repository, it ends like this:

```csharp
GetPostsByCreator(...)
GetPostsByTitle(...)
GetPostsByCreatorAndTitle(...)
GetPostsByCreatorAndTitlePaged(...)
// ...
```

## The Solution

A **query object** is one class for one query. The filter is a simple object, and the class builds the query from whatever is filled in. It lives in the **DAL** next to the repositories and uses the `DbContext` the same way they do:

```csharp
// DAL
public class PostFilter
{
    public string? Title { get; init; }
    public int? CreatorId { get; init; }
    public int Page { get; init; } = 1;
    public int PageSize { get; init; } = 10;
}

public interface IPostListQuery
{
    Task<PagedResult<Post>> ExecuteAsync(PostFilter filter, CancellationToken ct = default);
}

public class PostListQuery(AppDbContext context) : IPostListQuery
{
    public Task<PagedResult<Post>> ExecuteAsync(PostFilter filter, CancellationToken ct = default)
    {
        IQueryable<Post> query = context.Posts.AsNoTracking().Include(p => p.Creator);

        if (!string.IsNullOrWhiteSpace(filter.Title))
        {
            query = query.Where(p => p.Title.Contains(filter.Title));
        }

        if (filter.CreatorId is not null)
        {
            query = query.Where(p => p.CreatorId == filter.CreatorId);
        }

        return query
            .OrderByDescending(p => p.CreatedAt)
            .ThenByDescending(p => p.Id)
            .ToPagedResultAsync(filter.Page, filter.PageSize, ct);
    }
}
```

The business layer only knows the interface and maps the result to DTOs:

```csharp
// Business layer, registered as builder.Services.AddScoped<IPostListQuery, PostListQuery>();
public class PostService(IPostListQuery postListQuery) : IPostService
{
    public async Task<PagedResult<PostListItemDto>> SearchAsync(string? title, int page)
    {
        var result = await postListQuery.ExecuteAsync(new PostFilter { Title = title, Page = page });
        return result.Map(post => post.Adapt<PostListItemDto>());
    }
}
```

- **One place** for one query: adding a new filter means one new property and one `if`
- **Repositories stay small**: CRUD for one entity. Complex reads go into query objects
- **Easy to test**: the service depends on `IPostListQuery`, which can be mocked like `IUnitOfWork`
- Fits the search form directly: the form fields map to the filter properties
